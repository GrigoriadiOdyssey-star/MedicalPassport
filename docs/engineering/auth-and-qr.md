# Доступ, согласие и QR P0

Статус: **proposed-specification**. Исходные модули: 14, 27, 29, 30, 32, 33, 53, 54, 81–83.

## Вход владельца

Проектное решение: внешний OIDC-поставщик, Authorization Code + PKCE. Собственные `/auth/login`, `/auth/register`, сброс пароля и отправка биометрии из модуля 54 не реализуются в API P0. Поставщик обеспечивает регистрацию, восстановление, подтверждение контакта, MFA и отзыв сессий; его выбор и интеграционный контракт — задача реализации. OAuth password grant не используется; security baseline сверяется с [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html).

API принимает только access token для своей audience и проверяет подпись, допустимый алгоритм, issuer, audience, exp, nbf и состояние локального аккаунта. ID token не является access token. Ротация ключей не должна открывать обход проверки. Предлагаемый TTL access token — 5 минут; отзыв у поставщика должен либо проверяться сервером на каждом запросе, либо максимальная задержка отзыва равна TTL и явно показывается пользователю. Для P0 выбирается проверка состояния сессии на каждом медицинском запросе; при недоступности проверки — 503. Этот выбор ещё нужно обеспечить возможностями поставщика.

Refresh token остаётся в защищённом хранилище клиента или в серверной сессии BFF; в браузере access token не пишется в localStorage и не попадает в URL. Если применяется BFF, cookies Secure/HttpOnly/SameSite, Origin/CSRF-проверка и лимиты сессии обязательны; BFF не является частью опубликованного API. Локальные `access_token`/`refresh_token` из исходной таблицы 29 удаляются из модели P0. Биометрический материал на сервер не передаётся; биометрия устройства может разблокировать локальные учётные данные.

## Разрешения

| Субъект | Чтение | Запись | Особые условия |
|---|---|---|---|
| Владелец | Свой профиль, записи, документы, согласия, grants, аудит | Свои записи, создание/отзыв согласий и grants | Проверенный access token + активный аккаунт |
| Получатель QR | Только разрешённый разовый снимок | Нет | Валидный bearer-секрет; личность/профессия получателя не подтверждается |
| Worker | Только данные конкретного задания | Карантин, экспорт, удаление | Отдельная сервисная роль и audit |
| Поддержка | Состояния и request_id | Нет медицинских изменений | Медицинские значения не отображаются |

Роль «doctor», поле `recipient_type` или название больницы не дают автоматический доступ. P0 не имеет Public-уровня с ФИО, кровью и контактом: до явного выбора разделов и согласия выдаётся ноль медицинских полей.

## Согласие

Перед созданием consent интерфейс показывает цель `share_passport`, выбранные разделы, предупреждение «любой держатель QR сможет один раз получить копию», срок и версию текста. Отдельно видны сведения, которые будут переданы. Scopes: `profile` (display_name, birth_date, blood_group, emergency_contact, allergy_status), `allergies` (активные записи), `medicines` (активные записи). В P0 документы доступны владельцу, но не распространяются через QR. Раздел `profile` может включать данные контактного лица; они не включаются молча.

Consent — запись разрешения на конкретную передачу, а не универсальное доказательство правомерности всей обработки. Срок 60–86 400 секунд; нет бессрочного QR. Отзыв consent атомарно отзывает все его grants. Сам отзыв хранится как событие; старые согласия не переписываются под новую версию текста. Активное согласие не расширяется: для нового scope создаётся новое.

## Протокол QR

1. Владелец создаёт consent, затем `POST /qr-grants` с его ID и подмножеством scopes. Предлагаемый срок по умолчанию — 15 минут, не более срока consent и 24 часов. Сервер выдаёт `grant_id`, `token`, `expires_at` один раз. Токен: 32 случайных байта криптографического генератора, base64url без padding (43 символа). В БД хранится SHA-256 digest случайного секрета, а не сам секрет.
2. Клиент формирует ссылку своего доверенного origin вида `/share#token=<secret>`. Ни имя, ни медданные, ни grant ID не требуются в QR. Фрагмент уменьшает попадание секрета в HTTP URL, но не делает QR некопируемым: браузер, сканер и скриншот могут его сохранить. Экран использует `Referrer-Policy: no-referrer`, строгую CSP, не включает сторонние скрипты/аналитику; сразу после чтения очищает fragment через history replacement. Фрагмент не пересылается на другой origin.
3. Получатель подтверждает открытие; клиент отправляет `POST /qr-resolve` с секретом в JSON body по HTTPS. GET, предпросмотр ссылки и антивирусный prefetch не расходуют grant. Proxy/APM/body-logging на этом маршруте выключены. Bearer-токен владельца здесь не требуется; это отдельная ограниченная capability, а не общедоступный профиль.
4. Сервер по digest находит grant, блокирует согласие и grant, проверяет сроки/отзыв/статус аккаунта, формирует снимок разрешённых разделов, записывает consumption и аудит и делает commit. Только затем отправляет ответ с `Cache-Control: no-store`. Время снимка и `provenance: self_reported` показываются получателю.
5. Второе предъявление, истечение, отзыв, неизвестный или неверный секрет дают одинаковый 404 `qr_unavailable`. Не возвращать сведения о владельце и причине отказа. Потеря сети после commit расходует grant: получатель просит владельца создать новый. Это выбранная семантика однократной выдачи.

Снимок ограничен 100 активными аллергиями и 100 лекарствами. Если лимит превышен, весь resolve завершается 409 `snapshot_too_large` без consumption; нельзя молча обрезать медицинские сведения. Используется актуальная согласованная версия данных на момент resolve, а не скрытый устаревший кеш. Пользователь может отозвать уже использованный grant, однако уже скачанную копию это не удалит. QR никогда не обещает вызов скорой помощи или подтверждение личности.

## Защита и негативная приёмка

Начальные лимиты реализации: 60 resolve-попыток/минуту на IP, 10 созданий grant/минуту на владельца, 120 обычных JSON-запросов/минуту на владельца. 429 включает Retry-After; решение о повышении лимита — по измерениям. Защита не должна раскрывать, существовал ли секрет. IP-данные ограничиваются сроком и назначением; обычный audit получателя хранит pseudonymous actor, а не скрытое геослежение.

Обязательные сценарии: чужой UUID →404; поддельная подпись/issuer/audience →401; неизвестный scope →422; просроченный consent →409; конкурентные resolve →один 200; отзыв до commit resolve →отказ; неработающий audit →503; сбой после consumption →повторный отказ; история и логи не содержат token; пустые аллергии не превращаются в «аллергий нет»; замена исходного consent_id на чужой →404.
