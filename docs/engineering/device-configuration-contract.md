# Device configuration evidence — bounded data contract

MASTER-06 connects original IDs 4628, 5104 and 5115 to [CAP-DEVICES](../canonical/master06/CAP-DEVICES.md). [Schema](../../specs/device-configuration.schema.json) and [targeted checks](../../scripts/device-configuration-contract.mjs) specify evidence records, not programming/control endpoints or a runtime service.

Records require patient/tenant/device identity, sequential version and predecessor, effective/recorded timestamps, event, source record/version/hash/author, review state and settings. Numeric settings require an explicit unit; dimensionless values use an explicitly declared unit such as `1`. Codes and units still need device-specific terminology/compatibility approval. Actual-event records cannot claim a future effective event; plans require a separate future contract. All schema object levels reject undeclared fields. The JavaScript checks add predecessor, context and duplicate-setting constraints; they do not implement a full JSON Schema validator or validate clinical setting ranges.

Replacement closes the old physical device identity. A replacement device starts its own verified identity/history. Explantation is not an active configuration. Unverified/rejected latest records, missing predecessors, conflicting versions and regressing event times cannot cause silent fallback to an older record labelled current. Queries include both effective and recorded cutoffs to prevent later knowledge entering an earlier view. Caller authorization, source signature/authenticity, complete pagination and conflict reconciliation remain separate required services.

Records are immutable snapshots: `recorded_at` is when the entire snapshot, including its review state, became available. Later review must append a new version with its own recorded timestamp; mutating an older snapshot's review would invalidate historical queries. An eventual event-store adapter must enforce that rule and reject retroactive timestamp rewriting; this pure selector cannot establish storage authenticity.

`LATEST_VERIFIED_DOCUMENTED` means the latest eligible documented record, **not proof of a live physical device setting**. The selector never changes source data or sends commands. The reviewer ID is provenance, not cryptographic approval. MRI compatibility remains tied to the specific manufacturer/device/model evidence and approved workflow, not a generic device class or this record selector.

Remaining data gates: partner/device terminology packs, precise MRI/configuration evidence profiles, retrospective-correction semantics, imported partial-history reconciliation, full-schema tooling, retention/authorization enforcement, clinical ranges and signed review authenticity. Remaining testing gates include runtime/partner integration, device clock/signal-quality cases, usability and clinical acceptance. Data/testing evidence advances to PARTIAL_EVIDENCE for CAP-DEVICES; implementation readiness remains false.
