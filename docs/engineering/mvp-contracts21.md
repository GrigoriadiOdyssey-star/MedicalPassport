# MASTER21: engineering contract for the existing adult allergy slice

## Scope and status unit

The seven existing owners implement one workflow: an authenticated, independently bound adult patient selects one existing attributed allergy record, grants one verified clinician time-bounded read access, inspects receipts and withdraws the grant. Readiness is assessed for each owner's complete **MVP-scoped contract**, not its full canonical capability. No full-owner promotion follows. Medication, documents, QR, emergency overrides, external FHIR imports, minors/representatives, AI, diagnosis and clinical writeback remain excluded. All legacy requirements remain in their original canonical specifications.

This addendum supplies the six missing bounded engineering designs. Audit inherits MASTER16/18/19. External clinical/legal/identity approvals are release gates, not prerequisites to writing synthetic-only code. No patient use or production deployment is approved.

## Shared trust and deployment boundary

Build a modular application using the MASTER19 single relational transaction boundary. Identity, Security, Consent, Data, Allergy, Profile and Audit remain logical ownership boundaries; no new service owner. Store adapters are internal server-only ports, not public endpoints. The application does not accept caller-supplied subject, tenant, clinician role, verified age, policy approval or source verification. Only a configured server adapter supplies trusted context.

Development uses `SYNTHETIC` mode, a local fixed registry and labels every view as synthetic. The provided adapters reject any other mode and any fixture outside the synthetic identifier namespace. They have no network, credentials, persistent storage or actual authentication. Production builds must exclude the mock module. Startup must refuse real-patient mode unless signed deployment configuration binds approved issuer/adapters, current policy, clinical release evidence and country scope; the mock cannot satisfy these checks. Configuration parsers alone do not authenticate approvals.

The production identity adapter must validate its provider's authentication result before producing context: expected issuer/audience, verified signature and current trust key, expiry, replay/session revocation and exact tenant registration. Never fetch a key URL from an untrusted token, trust an algorithm chosen by the token, or infer patient/clinician authority from email, name, login or generic role. Provider selection, real credentials and conformance remain deployment gates. The port remains independent of provider transport; a future adapter needs its own versioned transport contract and acceptance tests.

## Identity: purpose, actors, permissions and data

Identity resolves current session, account-to-patient binding and clinician role. Actors are a bound adult patient, a verified clinician, and authenticated internal service; an operator has aggregate telemetry only. A patient account cannot self-assert adulthood or ownership. Clinician role references are independent of patient binding. Recovery, credential reset, MFA replacement, role withdrawal and binding changes increment an epoch and invalidate old sessions before further reads; they never transfer grants to a new subject automatically. Self-service registration, MFA-provider UI and recovery implementation are external-provider flows in this bounded profile; they cannot bypass epoch invalidation.

Persist IdentitySession keyed by (tenant, session_reference), SubjectBinding keyed by (tenant, subject_id, patient_id, binding_version), RoleAttestation keyed by (tenant, role_reference, role_version) and TrustConfig keyed by (issuer, trust_epoch). All validity times are integer UTC milliseconds; expiry equality is expired. Store verification source references, not credentials or identity documents, in the clinical database. Session and binding epochs are positive integers. An ambiguous binding, unknown adult status, withdrawn role or stale trust epoch denies.

`resolveSession(session_reference, now_ms)` returns the closed `identity_context` in `specs/mvp-ports21.schema.json`, or `UNAUTHENTICATED`/`UNAVAILABLE`; `resolveRecipient(role_reference, now_ms)` is an internal lookup of a registered verified clinician for the same tenant, never a public role directory. Each request obtains current state, not a cached ALLOW. The context carries tenant, subject, session, actor kind, patient binding (patient only), role reference (clinician only), verification/expiry times and epochs. Source evidence must establish age/role; schema syntax alone cannot. A clinician context has no inferred patient binding.

## Security: enforcement and release admission

Security owns current decision and release admission. Its internal input is verified context + current grant + current source snapshot + current deployment/purpose policy + operation. MASTER09 access envelopes and MASTER17 actions are retained. Map external `TREATMENT_REVIEW` to the existing internal `patient_authorized_review` exactly; no free-text purpose substitution. Required actions: own-source selection, grant creation/withdrawal, granted clinician allergy read, and patient self-receipt query. All other actions deny.

For clinician read, match tenant across identity/grant/source; subject's current clinician role to grant recipient; source patient/ID/version to grant; policy version to grant; ACTIVE grant; unexpired grant/role/session; active source; verified adult eligibility of the grant's patient. No stale or conflicting source revision is selected implicitly. A schema-valid role/patient ID is not authority. Unknown adapter/store state returns unavailable. External missing/inaccessible resources share the inherited uniform 404; internal denial reasons stay in protected metadata.

At admission acquire tenant integrity-stream lock then grant then the current source/admission state in that order. Writers for source correction, policy tightening, session/role revocation and patient-binding changes must participate in the same admission protocol: invalidate epochs and linearize before subsequent admissions. The production provider adapter must obtain a current bounded attestation under that protocol, or fail unavailable. Do not promise instantaneous remote revocation when the provider cannot meet it. A single admitted non-streaming response may complete within 5 seconds; after expiry reauthorize. Revocation cannot recall prior admitted/delivered bytes. Tests must inject revocation immediately before and after the admission boundary.

Patient receipt queries check current subject/patient binding and `audit.receipts.read_self`. A REVOKED/EXPIRED clinical grant remains queryable by the current authorized patient. Session/binding/receipt-policy revocation denies it. No clinical grant is needed to read one's already retained accountability history. Audit's pre-release append is required; an ALLOW without durable receipt cannot release data.

## Consent: ownership, API, state machine and persistence

Consent owns grant state and purpose/recipient/expiry, not enforcement. Keep MASTER17 `grant_create`, `grant_state`, `grant_revoke`, error and lifecycle event schemas unchanged. Public operations remain POST /v1/disclosure-grants and POST /v1/disclosure-grants/{id}/revoke. The server binds tenant/creator/patient, checks current adult binding, owned current source version and verified same-tenant clinician. A mismatched policy version or requested TTL outside the configured positive maximum denies. No default universal consent duration is introduced. Synthetic fixtures use 60 seconds; this is not production policy.

DisclosureGrant stores the existing closed state fields under (tenant, grant_id), with unique create dedupe key (tenant, subject, operation, Idempotency-Key). Commit grant, dedupe fingerprint, lifecycle outbox and audit together. ACTIVE can become REVOKED or be effectively EXPIRED by time; neither transition can reactivate. Revoke requires current creator binding and expected version; same authorized idempotent retry returns its original withdrawal result, a changed-body retry conflicts. Regrant creates a new ID after fresh source/role/policy checks. Source amendment invalidates an existing version-bound grant; it does not authorize the new version.

Persist a separate GrantAuthority row keyed by (tenant, grant_id), with patient_binding_version, recipient_role_version and policy_epoch captured at creation. Its closed `grant_authority` schema is in the new port package. Compare these values with current trusted state at clinician admission. Do not add them to or silently alter the published MASTER17 grant-state response. Changed authority invalidates future clinician admission until a fresh grant; patient historical receipts continue under current patient self-read authorization.

## Data and Allergy: source authority and clinical meaning

Data owns identity/provenance/version binding; Allergy owns assertion meaning and immutable source revisions. The internal port `readExact(tenant, patient, record, version)` returns `allergy_source` or uniform NOT_FOUND/UNAVAILABLE. Only a registered server source adapter may create snapshots. This MVP has no public clinical mutation or ingestion API. Initial data are synthetic fixtures in development and already ingested, accepted source records in a later approved deployment.

Persist SourceRecord keyed by (tenant, patient, record_id, record_version), unique current pointer keyed by (tenant, patient, record_id), with source_reference, source_digest, observed_at_ms (nullable), current flag, assertion and verification fields. The immutable snapshot digest covers the exact stored source representation; it is provenance integrity, not proof of clinical truth. Server time, record version and observed clinical time are distinct. No similarity-based patient matching, patient merge or unmerge occurs in MVP: ambiguity quarantines the record and denies disclosure.

Allergy states retain MASTER17: RECORDED, UNKNOWN, NOT_ASSESSED, NO_KNOWN_ALLERGY, with UNVERIFIED/CLINICIAN_CONFIRMED/CONFLICTING/UNKNOWN verification. For UNKNOWN/NOT_ASSESSED, verification is UNKNOWN and substance/reaction are null. NO_KNOWN_ALLERGY has null substance/reaction and is an attributed assertion, never inferred from an empty table. RECORDED may contain missing text; null stays missing. No AI completion, diagnosis, normalization to an assumed substance, or confirmed state without attributed evidence. The initial view displays source text as escaped plain text, not coded clinical inference. Licensed terminology mapping is a later optional exchange gate, not an invented code system.

Correction is an internal source adapter's new immutable version plus atomic current-pointer update and SourceVersionChanged outbox event. A revoked/deleted/quarantined source produces no clinical view; retain protected provenance under approved policy. There is no destructive correction or irreversible legacy import in this slice. Restoration must reconcile current pointers and source digests before reopening admission; old grants cannot silently refer to new versions.

## Profile: public view and frontend behavior

Profile owns the filtered projection, not a second patient record. GET /v1/disclosure-grants/{id}/allergy-view returns exactly the MASTER17 `allergy_view`, after current Security admission and Audit receipt. No extra patient demographics, blood group, credentials, internal digests or storage paths. Profile has no clinical table; assemble per admitted request, no browser/localStorage clinical cache, no public shared URL and no export in this slice.

The patient interface lists only independently authorized source records with version, origin and explicit uncertainty. Selecting one source enters recipient, purpose and expiry; show confirmation before creating a grant. Withdrawal has pending/success/unavailable states and explains that previously delivered information cannot be recalled. The clinician view shows source, version, assertion, verification and freshness without green-safe inference. Never render an empty response as no known allergy. Escape source text and preserve nullable text explicitly as not supplied. No drug recommendation, dosage or emergency message is generated.

The initial picker contains one explicitly supplied existing record reference (a synthetic fixture in development), not a whole-record search. POST /v1/allergy-selection takes the closed `selection_request` (record ID and expected version) and returns `selection_view`. Identity is obtained from current server context; the operation accepts only an active bound adult patient, exact owned current source and enabled policy, and commits an Audit access-attempt receipt before returning 200. Authentication failure is 401, inaccessible/missing/foreign or mismatched version is uniform 404, syntax is 400 and dependency failure is 503. This preview has no side effect on clinical data and is no-store. Retry may create a separately identified access-attempt event. No caller-supplied clinical fields or patient identifiers are accepted. Reuse MASTER16 action READ, outcome PENDING and producer profile_selection, bound to the source reference and current policy; this records an access attempt, not confirmed network delivery. Before a grant exists, serialize tenant stream then source row; do not invent a grant ID. These source-selection events remain in protected Audit storage and are outside the grant-specific MASTER18 receipt query. This is not a claim that the receipt query exposes all patient audit activity.

Patient receipt view inherits MASTER18/19: attempt versus delivery wording, withheld actor, snapshot/retention limits and unauthorized clinical role denial. Keyboard navigation, visible focus, labelled controls, non-colour-only status and accessible error recovery are acceptance requirements. Wrong-patient, unknown-state and receipt-comprehension cases need qualified clinical/human-factors review before patient use.

## Shared events, recovery, privacy and interoperability

Use MASTER17 GrantCreated, GrantWithdrawn, SourceVersionChanged, AccessAllowed and AccessDenied, with MASTER16 Audit envelopes. Identity/policy invalidation is synchronously reflected in current epochs; the bounded profile adds no asynchronous permission-grant event. External identity-provider events may trigger epoch updates only through verified adapter callbacks. Callback loss makes current attestation unavailable, not permanently trusted. Outbox and recovery use MASTER20 shared contracts once; no duplicated specialty policy. This contract does not claim mock tests prove SQL locking or actual provider revocation.

Denials never change clinical source or grant state. Fail unavailable on identity/policy/source/audit loss; no partial clinical response or stale fallback. Restart/restore quarantines reads until source/grant/policy/identity/audit/dedupe/outbox and epochs reconcile. Expire admission/cursor leases. Identical retries preserve results; conflicting retries fail. Release and recovery must be proven with the actual relational store during implementation acceptance.

Use the MASTER17 typed jurisdiction retention policy. Policy configuration also pins consent text version, positive grant TTL limit, issuer/role evidence validity, visible actor policy and applicability to adult single-record disclosure. Missing/unapproved production policy blocks activation and deletion. Hold overrides deletion. Record expiry, grant expiry, session expiry and legal retention are different clocks. Secrets are deployment secret references, never values in repository/config fixtures. No logs, metric labels or traces contain patient IDs, source text, tokens or cursors. Use correlation IDs only in protected logs.

This is internal EDHT JSON. FHIR/lab/pharmacy/notification adapters are NOT_REQUIRED by the inherited MVP dependency graph and must not be added to the initial build. Their interfaces remain future-wave specifications; the sandbox returns NOT_IN_MVP rather than fabricating integration success. Twin and Precision Pharmacology remain later waves with the existing canonical contracts intact.

## Observability, testing, acceptance, versioning and migration

Measure bounded aggregate operation latency, denied/unavailable outcomes, outbox age, replay conflict and recovery reconciliation failures. Alert on persistent admission/audit failure or integrity mismatch within 60 seconds. Synthetic test load: 20 grant/read operations and 20 receipt queries per second for 10 minutes; p99 end-to-end read <=1 second and audit append <=500ms; no acknowledged state loss across injected restart. These are targets, not measurements. A named operational owner and capacity envelope are deployment acceptance gates.

Required implementation tests: patient source selection → grant → exact clinician view → durable receipt → revoke → denied subsequent clinician read → patient historical receipt access; wrong tenant/patient/recipient/purpose; stale source/policy/role/binding/session epoch; unknown age; deadline equality; altered-body retry; ambiguous source; adapter failures; mock rejected in production; escaped adversarial source text; concurrent revoke/correction/read; crash before/after commit; outbox replay and restore; cache/log leakage; accessible unknown/negative/conflicting displays. Schema and mock oracle tests provide engineering evidence only. Database concurrency, HTTP/browser, security and load tests remain backlog acceptance tasks.

Use shared MASTER20 immutable contract majors. Existing MASTER17/18 endpoints and schema versions are unchanged; new internal ports are version 1. There is no legacy import in MVP. Introduce SQL migrations with forward-only immutable source preservation, dry-run count/digest reconciliation and new storage epochs; if rollback cannot read acknowledged state, quarantine and roll forward. Never rollback clinical truth, revoked grants or policy epochs to make old binaries work.

Every engineering-ready profile requires all 17 MASTER21 criteria, this shared contract plus owner-specific schema/API references, explicit external gates and a dependency-ordered backlog. A missing schema, unavailable required evidence or altered inherited contract prevents the build-gate promotion. ENGINEERING_READY permits synthetic implementation; CLINICAL_RELEASE_READY, LEGAL_RELEASE_READY, EXTERNAL_INTEGRATION_READY and PRODUCTION_READY remain false until independently evidenced.
